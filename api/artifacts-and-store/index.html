    Artifacts and store¶

    What Hylo learns is saved as an artifact: a directory with a content digest and a record of what it was built from, sealed unless marked mutable. Configs can refer to runs and artifacts by store id instead of path. Scorecards and active versions are the formats bench and serve exchange. User guides: learning, the store, benchmarking, deployment.

    Artifacts¶

    artifact ¶

    Derived artifacts (RFC-0004): everything the system learns is a versioned, digest-pinned directory with provenance.

    The trace store is the single source of truth. Action memories, critics, value models, fine-tuned weights, datasets, judges are all derived from traces (or from external data sources) by a builder, and each one carries an artifact.json manifest: what it is, which role it plays, a content digest, and which runs / splits it was built from. Three roles, three trust paths:

    • behaviour changes what the robot does (memory, critic, noise policy, weights): only the RSI gate activates it;
    • instrument measures or labels (success judge, progress model, world model): trusted only after calibration against ground truth, never the gate's verdict;
    • proposal only changes what gets proposed (lessons, skill index); curated by outcome votes.

    One split guard for every builder: development splits (search, search_val) and calibrated external sources may be read; gate and held-out data never. The gate re-checks the provenance of every artifact a candidate references, so a leak is caught even if a builder forgot the guard.

    Store¶

    store ¶

    Run and artifact store (hylo.store/v0.1): global ids, references instead of paths, deletion protection, sync.

    A store is a directory tree on one machine (this machine's profile says where: hylo store init PATH, else $HYLO_STORE, else ./runs). Runs (directories with an evallog.json) and sealed artifacts (an artifact.json) anywhere under it get an id:

    run:<run_id>                       run ids are unique (they end in a random suffix)
artifact:<name>@<digest>           name from the manifest, digest = content digest (a prefix of >= 8 hex works)
artifact:<name>                    allowed when exactly one artifact has that name; the run manifest pins it

    Configs reference artifacts by id (critic: {path: artifact:l10-v1@3d8d6096f7111acc}); the registry resolves ids to this machine's paths when it builds a component, after the experiment digest is taken, so the same config means the same content on every machine. Learner job inputs accept run and artifact ids too.

    The index (/.hylo-store/index.json) is a cache, rebuilt by walking the tree when an id is not found. It also records who refers to what: an artifact's provenance (the runs and artifacts it was built from) and a campaign's archive and promotion ledger. hylo store rm refuses to delete anything still referred to unless forced, and a forced or plain removal leaves a tombstone, so a dangling reference says what happened instead of "not found".

    hylo store push|pull HOST:PATH [ID ...] copies runs and artifacts between machines with rsync (runs from the robot computer to the workstation, artifacts the other way). Sealed artifacts are never overwritten: the same path holding a different digest on the other side is a conflict and nothing is copied.

    Scorecards¶

    scorecard ¶

    Scorecards (hylo.scorecard/v0.1): the result of running one policy under one benchmark protocol.

    Written by hylo-bench (hylo bench run), read by leaderboards, the catalog, the playground and the project site, so the format lives here. A scorecard is self-contained: the protocol and policy it measured, the headline metrics with a 95% interval on success, per-task success, and the per-episode outcomes (episodes, keyed "task#seed") that let two scorecards of the same protocol be compared pairwise.

    {"schema_version": "hylo.scorecard/v0.1", "protocol": "libero-10", "protocol_version": "1",
 "protocol_digest": "...", "policy": "smolvla", "agent": {"type": ..., "params": ...},
 "metrics": {"success_mean": 0.54, "steps_mean": 312.0, ...}, "success_ci95": [0.40, 0.67],
 "per_task": {"libero_10/0": {"success": 0.6, "n": 5}, ...}, "episodes": {"libero_10/0#30000": 1.0, ...},
 "run_dir": "runs/...", "config_digest": "...", "created_at": ...}

    Active versions¶

    deployment ¶

    The active version of an improvement campaign, as a file (hylo.active/v0.1).

    The campaign (hylo-evolve) writes <campaign>/active.json whenever its active version changes: at start, on a promotion, on an approval, on a rollback. Anything that deploys the campaign's current behaviour (the policy server in hylo-serve) reads only this file, so the deploying side needs neither the improvement code nor the candidate registry, and the file can be copied to another machine.

    {"schema_version": "hylo.active/v0.1", "campaign": "libero10-steering", "version": "cand-1a2b3c4d5e",
 "agent": {"type": "lerobot.steered", "params": {...}}, "patch": {"agent.params.kp": 2.0},
 "lineage": ["cand-1a2b3c4d5e"], "updated_at": 1793400000.0}

    version is None while the base configuration is active. agent is the fully resolved agent spec (base config with the lineage's patches applied), so a reader builds it with the registry and nothing else.
