    Kernel¶

    EpisodeRunner is the one episode loop; evaluation, Studio's live sandbox and the workcell all use it. It runs an environment and an agent through the safety shield, in sync or realtime timing. Events go to an EventBus; a TraceStore writes them to the run's trace. See also the execution lifecycle.

    Episode loop¶

    kernel ¶

    Execution kernel: the one episode loop, used for evaluation, learning rollouts and deployment.

    env.reset -> agent.reset -> loop[ request a chunk (when the queue runs low) -> merge it when it arrives
                                  -> SafetyShield.review -> env.step -> agent.on_step ]
          -> episode.end -> agent.on_episode_end

    Timing decides how policy time relates to robot time: - "sync" (default): the world waits for every policy call; a chunk is requested when the queue is empty and runs execution_steps actions. Deterministic; what benchmarks have always measured. - "realtime": the robot keeps moving while the policy thinks (LeRobot async inference, openpi's runtime, vla-eval's live runner): a chunk is requested when at most refill_steps actions remain, a chunk computed from the observation of step s that arrives at step t has its first t - s actions dropped (aligned merge), an empty queue executes a hold action, and a watchdog aborts after max_hold_steps consecutive holds. On the "virtual" clock the policy latency is measured (or fixed by latency_s) and the steps it would have taken run before the chunk is merged: deterministic, so benchmarks can measure deployment behaviour. On the "wall" clock the policy runs in a worker thread and the loop ticks at the control rate: the workcell next to a robot.

    Both modes share the SafetyShield, the trace events, error classification and the operator channel (stop, latched e-stop, reset confirmation, outcome verdicts), so what the gate approved in simulation is what the robot runs.

    This is "driven mode". In "served mode" (an external harness owns the loop) the same Agent + SafetyShield + trace are wrapped by a protocol adapter; see docs/execution-lifecycle.md.

    Traces¶

    trace ¶

    Event-sourced, replayable episode trace.

    Layout of a run directory

    /manifest.json RunManifest (config hash, versions, seeds) /episodes/.jsonl one Event per line, arrays inline when small /blobs/.npy large arrays (images, point clouds), content-addressed /evallog.json aggregated scores; points back at episode files /seal.json optional: the run's file inventory, written by hylo seal

    Hash chain (hylo.trace/v0.2): every event line carries prev (the previous line's hash, "" for the first) and h, the sha256 of the line's canonical JSON without h. Blobs are named by their own digest, so the chain covers them too. hylo.core.seal.verify_chain finds the first line that was changed, removed or reordered. Lines written before the chain existed have neither key and are reported as unchained, not as broken.

    Scorers and shadow replay read only this; they never call the Agent or the Environment.

    BLOB_THRESHOLD_BYTES module-attribute ¶

    BLOB_THRESHOLD_BYTES = 64 * 1024
