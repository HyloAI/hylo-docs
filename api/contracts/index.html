    Contracts¶

    Every plugin group's contract lives in hylo-core, so a plugin's contract comes from hylo-core alone. This page lists what a plugin must provide and the data that passes between the episode loop, environments and agents. The plugin system explains how plugins are registered; the interface notes explain the design behind each contract; the plugin catalogue lists what implements them.

    Environments¶

    env ¶

    Environment contract. An Environment = Simulator + Task logic behind reset/step.

    Optional capabilities are declared in EnvSpec.capabilities and exposed through separate protocols, never by duck-typing, so the kernel can refuse a run that needs a missing capability.

    Must be cheap: no simulator construction (ManiSkill builds obs space via a real reset).

    Policies¶

    policy ¶

    Policies (plugin group "policies"): action-chunk generators that agents run, steer and compose.

    An Agent is what the kernel talks to (core.agent). A ChunkPolicy is the model inside: given an observation it draws action chunks, one per noise seed. Separating the two lets one policy be run, steered (seeded noise, sample-and-select, recovery rules), temporally ensembled (ACT), shadowed or memory-steered by agents in hylo-agents without the policy knowing, and lets one agent wrap any policy by configuration:

    agent: {type: policy, params: {policy: {type: policy.flow, params: {path: artifacts/flow}}}}
agent: {type: steered, params: {sampler: {type: lerobot, params: {repo_id: lerobot/smolvla_libero}},
                                steering: {n_samples: 4, selector: medoid}}}

    Deterministic policies (regression, retrieval, scripted) ignore the seeds and return identical samples. Stochastic ones (diffusion, flow matching, sampled tokens) must derive their randomness from the seeds only, so a candidate and its parent face the same noise on the same init state and an episode can be replayed.

    Reasoning components¶

    reasoning ¶

    Reasoning plugin contracts, one per role (each its own plugin group and version):

    • reasoners (hylo.reasoner): the slow, event-triggered part of an agent; turns observations and memory into a Decision (a subgoal, a skill, an abort), with begin / deliberate / end around an episode.

    Robots and scenes¶

    These data contracts connect environments with task-strategy tools and program agents. They do not import a simulator.

    robot ¶

    Robot description contract (hylo.robot/v0.1): what a manipulation environment tells tool-using agents about its robot, so the same perception, kinematics and planning tools (hylo-manip) work on every simulator and robot.

    An environment that supports tool use puts a RobotSpec in EnvSpec.robot (so it also travels over the remote protocols) and follows the observation layout below. Nothing here changes how the kernel runs an episode: actions are still joint-position targets reviewed by the SafetyShield, one per control step.

    Frames and units: metres and radians; the environment's world frame with +z up; poses are 4x4 homogeneous matrices given as nested lists. Cameras use the OpenCV optical frame (x right, y down, z forward).

    The tool centre point (TCP) is defined the same way for every hand, so a grasp means the same on every robot:

      origin  where a held object's centre sits (between the pads of a parallel gripper; among the fingers of a
          dexterous hand, a few centimetres in front of the palm)
  +x      approach: the direction the hand moves to reach into an object
  +y      closing axis: the pads close along it (dexterous: the thumb-to-fingers direction)
  +z      x cross y

    Observation layout of a manipulation environment (keys of Observation):

      state["q.<arm>"]           measured joint positions of that arm, in ArmSpec.joints order
  state["hand.<arm>"]        measured hand state in command units (parallel: one value, 0 closed .. 1 open), not the
                             last command: pads that stop short of closed tell the tools something is held
  state["base"]              [x, y, yaw] of a mobile base (only when RobotSpec.mobile_base)
  images["<cam>"]            RGB, (H, W, 3) uint8
  images["<cam>.depth"]      depth in metres along the optical axis, (H, W) float32; 0 or non-finite: no return
  images["<cam>.seg"]        instance ids, (H, W) int32, only when the environment was configured to give
                             segmentation (a privileged observation: it is part of the measured config)
  extra["cameras"]["<cam>"]  {"K": 3x3, "T_world_cam": 4x4}: intrinsics and the current camera pose
  extra["segments"]          {"<id>": "<label>"} for the instance ids above

    Action layout: the concatenation, in RobotSpec.arms order, of each arm's joint targets followed by its hand command (ArmSpec.action_slice / hand_slice say where each sits).

    scene ¶

    Table-top scene contract (hylo.scene/v0.1): a manipulation task written as data, so a model can author it, a checker can validate it and an environment (bench: mujoco.panda_scene) can load it.

    It lives in hylo-core because it crosses the harness / bench boundary: the harness writes and checks scenes (the scene builder of RFC-0006 part 8), bench environments load them, and neither side may import the other.

    Frames and units: metres; ANGLES IN DEGREES (unlike hylo.robot, so hand-written and model-written files stay readable); world frame of the environment, +z up, table top at z = 0 unless the environment says otherwise.

    A scene is a list of objects and a success predicate:

      object   one rigid body: a primitive (box, cylinder, sphere, capsule, mesh) or a ready-made container
           (tray: open box; cup: open cylinder), or a list of primitive `parts`; name (identifier), label (the
           words an instruction uses), colour, mass, friction
  pose     fixed start pose (pos [x, y] or [x, y, z]; z omitted: resting on the table or on `on`), or `region`:
           a box of start positions and a yaw range sampled from the episode seed (seeded variation)
  fixed    a fixture: does not move (no joint to the world)
  parent   attached to another object, rigidly or through one `joint` (slide or hinge): drawers, doors, lids,
           buttons; its pose is then in the parent's frame
  success  a declarative predicate over object poses and joint states, evaluated after every control step

    Predicates (field op): on, inside, near, above, upright, lifted, row, joint_at_least, joint_at_most, not, all_of, any_of, sequence. Object predicates require the object at rest and released (not touching the hand) unless released: false. sequence latches: each term must become true after the previous ones did.

    Instruments¶

    instrument ¶

    Instruments (RFC-0004): learned components that measure or label instead of act.

    A success judge or progress model labels episodes (so memory and training data can be written without simulator ground truth); a world model pre-screens candidates. Instruments are trusted through calibration, not the gate: hylo.learn.calibrate scores a judge against simulator outcomes on runs the judge was not built from and stores the CalibrationReport in the judge's artifact manifest. An instrument never decides a gate verdict: in simulation the gate always scores with ground truth, and a world model may only choose which candidates are worth real evaluation budget.

    Safety¶

    safety ¶

    SafetyShield: the single, non-bypassable checkpoint between any Agent and any Environment.

    • Built by the kernel from the EnvSpec plus config; Agents never see or construct it.
    • Mandatory guards (finite check, bounds clamp) are always installed; config can only add guards or tighten limits. RSI candidates cannot target the safety.* config scope (evolve/candidate.py).
    • Extra guards are plugins ("guards" group): safety: {guards: [{type: keep_out, params: {...}}]}. They run between the mandatory finite check (first) and bounds clamp (last), so no plugin can let a non-finite or out-of-bounds action through. Built in: delta_limit, workspace, norm_limit, keep_out.
    • Rotation-aware: per-dimension clamping is refused for quaternion / rot6d dims (inspect-robots approver.py makes the same choice).
