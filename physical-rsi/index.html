    Physical RSI¶

    Use task outcomes to propose changes, compare them with the current agent and carry adopted versions into later runs. Hylo connects worlds, agents, memory and skills through this improvement loop.

    People define the tasks, success checks and operating boundaries. Campaign promotion defaults to auto; configure approval: manual for anything that will run on hardware and validate the target deployment.

    Motivation¶

    Running a robot autonomously does not make its improvement autonomous. Someone still has to inspect failures, choose a change, compare it with the current version and decide whether to keep it. Physical RSI connects those steps so an adopted improvement becomes the starting point for the next round.

    The change can be a controller setting, a recovery rule, a prompt, a program, a memory bank or learned weights. This lets a system improve a useful part of its behaviour without requiring a new model-training run every time. Which changes are available depends on the agent and its compatible generators or learners.

    Physical feedback¶

    The proposal and its evaluation have different roles. A model may suggest a better grasp or write a sorting program, but its explanation is not evidence that the task succeeded. Task checks measure what happened: whether an object was lifted, where it ended up, whether a controller reached its target, and which interventions occurred. In simulation, scoring can use privileged state while the agent receives only its permitted observations.

    This separation matters because an optimiser can improve a score by exploiting its definition. Success conditions must be fixed outside the candidate, and evaluation must cover the claim being made. Passing one scene's check establishes that result; improvement across a task family requires a comparison on a declared set of tasks.

    Improvement loop¶

    Step Capability Guide
    Build Create scenes, robots and task conditions Worlds
    Run Execute an agent and record actions and outcomes Experiments
    Improve Produce candidate settings, programs or learned artifacts Campaigns, Learning
    Verify Compare frozen candidates under declared conditions Benchmarking
    Deploy Activate a version for later execution and retain rollback Deployment

    Each round starts from the version the previous round adopted. A rejected candidate stays in the archive; it does not replace the active version. Task checks provide feedback independently of an agent's own summary.

    Campaigns¶

    A campaign diagnoses failures, asks a generator for changes, screens candidates and applies a paired promotion gate. It records the evidence and version history. Generators may propose settings, steering rules, programs or learner artifacts. They cannot change the protected safety, scoring or benchmark settings.

    Selection and confirmation¶

    Development runs expose failures; a separate screening split helps choose among candidates. The gate then compares a selected candidate with its parent on matched initial states. Pairing reduces differences caused by which scenes happened to be easy. Regression and safety checks can veto a candidate even when its average success rate improves. Matching seeds also requires a consistent model runtime and batching protocol when controlling policy randomness.

    The held-out report is separate from candidate selection. These roles reduce selection bias, but the current campaign can reuse gate states across cycles and expose previous outcomes through its archive. They are not an unlimited supply of fresh tests; the split access rules describe that limit.

    Versioned progress¶

    A candidate names a configuration change and any sealed artifacts it needs. Their provenance records the data and settings used to produce them. Promotion records the parent, candidate and evidence; a rejected candidate remains in the archive without replacing the active version. Retaining failures helps later proposals avoid repeating them, while retaining versions makes rollback possible.

    Behaviour changes, measurement tools and proposal advice need different evidence. An agent change goes through the campaign gate; a learned judge needs calibration against known outcomes; a lesson earns credit through the outcomes of candidates that used it. A persuasive lesson or a calibrated judge does not by itself prove an agent has improved.

    Start with First improvement for a complete CPU example, then use Campaigns to configure your own loop.

    Reusable outputs¶

    • Agent versions retain adopted configuration changes and rollback history.
    • Artifacts retain weights, critics, world models, judges or memory banks with their provenance.
    • Skills retain reusable programs or procedures with applicability and verification evidence.

    Each output has its own validation path. A calibrated judge is an instrument; it does not become a promoted agent. A verified program skill is available for reuse; it does not deploy itself onto a robot.

    Inputs¶

    Bring a task and its success conditions, a simulation or robot interface, and a starting agent. Existing models, programs, demonstrations and recorded runs can supply that starting point. Follow Agents to choose the execution mode and Learning to ingest external data.

    Operation¶

    Serve runs agents through policy servers and workcells. Studio shows runs and campaigns and provides operator controls. Every executed action passes the safety shield. Rollback changes the active version; it does not undo physical actions.

    Keep development and evaluation data separate, retain observation conditions with results, and revalidate when the task or robot changes. Simulation evidence supports its stated conditions; hardware needs target validation.
