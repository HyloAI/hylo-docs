    Extending Hylo¶

    Source

    Maintained in hylo-harness: docs/extending.md.

    Everything that varies between methods is a plugin: a class that satisfies a small contract, registered under a name through a Python entry point (or referenced as module:attr). A plugin package never modifies Hylo. The examples below live in the plugins repository (hylo-plugins: packages/hylo-plugin-examples, module hylo_examples), written the way a third party would; run them from that repository (they use MuJoCo planar reach from hylo-bench).

    1. Start a plugin¶

    hylo plugin new learner my-recap          # also: policy, agent, guard, gate_test, online_learner, datasource, judge, generator
uv pip install -e plugins/hylo-plugin-my-recap
uv run pytest plugins/hylo-plugin-my-recap/tests          # the template passes its conformance check as generated
hylo plugin check learner my-recap                        # same check from the CLI, on any registered plugin
hylo plugins                                               # every plugin: contract version, maturity, licence

    Environments and agents are checked with hylo conformance CONFIG [--agent].

    Each plugin group is a versioned contract (hylo.policy/v0.1, ...; hylo.core.plugins.CONTRACTS). A plugin package declares what it implements in one dictionary, registered under the hylo.meta entry-point group (the template generates it):

    META = {"contracts": {"learners": "hylo.learner/v0.1"}, "maturity": "unverified",
        "plugins": {"learners/my-recap": {"weights": "...", "notes": "..."}}}     # per-plugin overrides, optional

    Maturity is implemented (run end to end on its target, with recorded runs), unverified, or needs-hardware; weights names the licence of model weights the plugin needs, the code licence is license in pyproject.toml. The registry refuses a plugin that declares another major version, or a newer minor version, than the core implements; hylo plugin check warns when a declaration is missing.

    surfaces a factory returning a Surface of ToolDefs (core/tooling.py) mujoco.world tools for models, people and coding agents: anything callable through hylo world chat, hylo mcp, the Studio and hylo roles Surface.call checks every call against its schema

    3. What a plugin gets for free, and what it cannot change¶

    For free: - store ids: configs reference artifacts as artifact:<name>@<digest>, resolved to this machine's path when your plugin is built (hylo store, hylo.core.store); your plugin receives a path as before; - the split guard: learners read development data only. Gate and held-out runs are refused at build time and again at the gate. - sealing and provenance; - running in any venv (launch); - resumable jobs; - the gate (cascade, sequential looks, Holm, regression and safety vetoes, held-out report); - traces, replay, A/B comparison; - the playground.

    By design, a plugin cannot change: - the protected configuration scopes (safety, benchmark, trace, scoring); - the mandatory safety guards (finite check first, bounds clamp last); - the rule that only the gate activates a behaviour artifact, and that instruments are trusted only after calibration.

    Candidates are configuration patches and can reference sealed program artifacts. Program agents and research sessions execute model-generated code with AST validation and a restricted Python namespace in the host process. These restrictions do not provide operating-system isolation. Campaign approval controls promotion after candidate evaluation; see program execution boundaries.

    Example Files Run
    A guard plugin that slows the robot inside a zone hylo_examples/guards.py, examples/configs/mujoco_guarded.yaml hylo run examples/configs/mujoco_guarded.yaml
    A gate on steps instead of success; a practical-significance gate hylo_examples/stats.py, examples/evolve/mujoco_steps_gate.yaml hylo evolve run examples/evolve/mujoco_steps_gate.yaml
    An online learner (cross-entropy method) as a candidate generator hylo_examples/online.py, examples/evolve/mujoco_online_cem.yaml hylo evolve run examples/evolve/mujoco_online_cem.yaml

    One reference policy per family, trained and scored on MuJoCo reach (bench) examples/policies/ in hylo-bench uv run python examples/policies/compare.py
    An offline learner, a judge, a data source, a generator, a policy, an agent hylo plugin new <group> <name> templates uv run pytest <package>/tests

    5. Policies: one contract, many families¶

    An agent is what the kernel runs; a policy (policies group) is the model inside it. Any policy plugin runs with {type: policy, params: {policy: SPEC}}, ACT-style with temporal_ensemble, or steered (seeded noise, sample-and-select, recovery rules) with {type: steered, params: {sampler: SPEC}}, and the reference policies of hylo-policies cover one example of each family (examples/policies/):

    Family Published methods Here
    Retrieval VINN policy.knn
    Regression BC with action chunks BC, BC-RNN, ACT's chunking policy.bc; ACT's temporal ensembling is the temporal_ensemble agent
    Diffusion / flow matching Diffusion Policy, pi0, SmolVLA, GR00T's action head policy.flow (flow matching); the LeRobot ones via lerobot
    Tokenized actions RT-1, OpenVLA, VQ-BeT, pi0-FAST policy.tokens (binned, independent heads)
    Model-based planning MPC, PETS, TD-MPC policy.mpc over a world_model.state artifact
    Large VLAs pi0 / pi0.5, SmolVLA, GR00T N1.5, OpenVLA lerobot (any LeRobot policy by repo id), openpi (an openpi server), or a new policy plugin

    6. Mapping published methods onto the extension points¶

    Method Plugins
    V-GPS, RoboMonkey (re-rank sampled actions) a learner for the value model, plus an agent that samples and selects
    Retrieve-then-Steer, DSRL (offline) a learner that builds a bank, plus a prior / noise steering agent
    Expert iteration, BC, RECAP (offline) a data source and labeler if needed, plus a learner producing weights
    SimpleVLA-RL / GRPO, DSRL (online), RECAP (iterative) an online learner: policies() returns the current policy, update() takes a step from the rollouts' traces
    GEPA, Eureka (prompt / reward search) a generator: prompts and reward weights are configuration values
    RoboArena-style pairwise evaluation a gate test on a preference metric
    FAIL-Detect / SAFE an instrument for the detector; a guard to act on it
    A new robot or simulator an environment (or a LeRobot Robot, through lerobot.robot)
    A new policy family (GR00T, OpenVLA, ...) an agent adapter, or serving it behind the openpi protocol
